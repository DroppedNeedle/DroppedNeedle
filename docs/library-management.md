# Library Management

Library Management writes MusicBrainz Picard-style tags, artwork and lyrics, and names and files your music, always behind a preview you check first. It is off until an admin enables it, and lives on the Library Management page (admins). How albums are scanned and identified is in [Your library](library.md).

## Previews and Apply

Pick library folders, artists, albums or single files, pick a profile, and make a preview. Nothing changes yet. The preview works through your files in the background and then lists every file with its new tags and its new path from the profile's naming script. Each file that will be left alone says why and what to do about it, for example "This album's edition is a best guess nobody has confirmed yet" with a pointer to confirm it. An album is changed as a whole: picking single files of an album that would move still moves the whole album, and if one of its files can't be managed, the rest of the album waits too and says so. Cover art, cue sheets, rip logs and lyrics files in the album folder (the profile's sidecar patterns) move with it; if one would land on an existing file, the album waits with that reason instead of overwriting anything. Renames that only change letter case work too.

Apply writes the albums one at a time; the operation page shows each file's result, and a file that failed says why. If the settings or library folders change after the preview, apply refuses and asks for a new preview. A preview stays usable for the preview retention in the Library Management settings (24 hours by default). Any finished run can be undone the same way: preview the undo, check it, apply it. Undo brings the sidecar files back as well. Files someone changed since are left alone and say so, and a run that was already undone can't be undone twice.

## Profiles and fields

A profile's field table has one row per tag, under the names v2 used, and each row says where its value comes from. From the album's edition: title, album, artist, artists, artist sort, album artist, album artists, album artist sort, track and disc numbers and totals, disc subtitle, date, original date, release status, country and type, compilation (set for Various Artists releases), ASIN, media, label, catalog number, barcode, ISRC, and the MusicBrainz recording, release track, release, release group, artist and album artist IDs. From the recording's and its works' credits (see [Credits and works](#credits-and-works)): work, MusicBrainz work ID, composer, lyricist, conductor, performer, arranger, remixer and producer, and engineer, mixer, DJ-mixer, writer and director.

MusicBrainz has no value for title sort, album sort, comment, copyright, encoded by, or the movement name, number and count, and DroppedNeedle never makes one up: the file keeps its value, "Replace" with "clear" removes it, and a tagging script or the tag editor can set it.

The two AcoustID fields come from the file's audio. The fingerprint is the Chromaprint print of its first two minutes, the same one identification uses, kept so a file is decoded once while it stays the same. The AcoustID ID is looked up with your AcoustID key and written only when AcoustID links that print to the file's own MusicBrainz recording. Without a key, or while AcoustID can't be reached, the file keeps its AcoustID ID and the preview says so; an album managed automatically waits for AcoustID and is looked at again by itself. A file shorter than a second gets a fingerprint but no ID. Prints count toward a run's half hour of audio analysis. Neither field is ever cleared, merge is not offered, and the Picard preset fills them only where a file has none.

The genre row is the Genres section's switch and mode. Merge is offered for the fields that hold several values. Profiles saved before keep writing what they wrote: a tag that used to be written along with another field (artist sort with artist, the release facts with album, original date with date, disc subtitle with disc number, the release track ID with the recording ID) takes that field's mode, the older spellings (`albumartist`, `track`, `disc`, `year`) fold into their field, and a preserved field still preserves the tags it covered. Profiles that already listed ISRC or album artists now write them. MP4 files have no place for performer or arranger: when a profile or a tagging script would set one there, the preview says so and the file keeps what it has.

## Tags, credits and artist names

### Tags and ID3 versions

A retag under Library Management writes the full set of MusicBrainz tags from the release the album was identified as, with the tag names Picard uses, so other players and taggers recognise the files. That includes each track's ISRC codes when MusicBrainz has them. WAV and AAC files are read-only and keep their tags.

An MP3 keeps its ID3 version, with one exception: an ID3v2.3 tag that also holds newer ID3v2.4 tags (Picard and iTunes write sort names that way, some taggers full dates or credits) is saved as ID3v2.4, so every tag keeps its own frame. The old format's year and day, original year, sort name and involved-people tags move to their ID3v2.4 places; where an old and a new tag hold different values, both stay and the new one is read. The preview of a management run says so for each such file. A few old players read only ID3v2.3. Undo and Restore originals put the values back; the tag stays ID3v2.4.

### Credits and works

Composer, lyricist, conductor, performer, arranger, remixer and producer come from the MusicBrainz relationships of the track's recording and of the works it performs, under the name the artist is credited as on that recording, as Picard writes them (with "Artist credit style" set to "Canonical names", under the artist's own MusicBrainz name). A performer is written the way Picard writes it, "Glenn Gould (piano)", "Ringo Starr (lead vocals)", "Beyoncé (guest vocals)", with the instrument list ID3 players read. Work is the performed work's title (left as it is when a recording performs several, as in a medley), and MusicBrainz work ID lists every performed work. The profile's Relationships settings choose which credit types are written; a type that is off, or the whole switch, leaves the file's tag as it is, and work and work ID are written either way. The credits are fetched once per album when a profile first writes them and kept with the album's edition for a week. When MusicBrainz can't be reached, a preview writes everything else and keeps the file's credits, saying so, and an album managed automatically waits and is looked at again by itself. Credits are never cleared because they could not be fetched; "Replace" with "clear" only removes a credit MusicBrainz says the track does not have. Custom editions keep the files' credits.

"Other roles", in the Relationships settings, writes the other credits Picard writes: engineer (MusicBrainz's engineer, audio, sound and live sound credits; mastering and recording engineers are not written, as in Picard), mixer, DJ-mixer, writer and director, each in its Picard tag (`ENGINEER`, `MIXER`, `DJMIXER`, `WRITER` and `DIRECTOR` in FLAC and Ogg; the ID3 involved-people list and `TXXX:Writer` and `TXXX:DIRECTOR` in MP3; `----:ENGINEER` and the like, `----:writer` and `©dir` in M4A). It also writes the credits Picard files under the main roles: a librettist as lyricist, an orchestrator or instrument or vocal arranger as arranger, and a chorus master, concertmaster or performing orchestra as a performer, "Berliner Philharmoniker (orchestra)". Such a credit needs its main role ticked too: an orchestra is written only when Performer is also on. A DJ-mixer credited for one disc of a release is not written. The Picard and Complete presets tick "Other roles", and a profile that already ticked "Other relationships" starts writing these credits at the album's next run, with the five new field rows added on replace; on any other profile, ticking it writes the five only where their field rows are on. Albums managed before have their credits fetched again once.

### Artist names

The profile's "Artist credit style" picks how the artist, artists, artist sort, album artist, album artists and album artist sort tags (and the credits) name an artist, as Picard does: as the release credits them ("Release credits", the default), or under each artist's own MusicBrainz name ("Canonical names"). With "Translate artist names" on, an artist is written under their primary alias in the first of your preferred locales MusicBrainz has one for ("en, en-GB, ja"; a locale also matches its regional variants, and a full match for a later locale beats a regional one for an earlier), with that alias's sort name. An artist with no such alias whose name is not in Latin script reads their sort name turned round ("Sakamoto, Ryuichi" becomes "Ryuichi Sakamoto"); with no preferred locale only that applies. Composers, performers and the other credits have no aliases in MusicBrainz's answer, so they are translated that way only. Various Artists is never translated. The artists' names and aliases are fetched once per album, in the same MusicBrainz request as the credits, and kept with the album's edition for a week. When MusicBrainz can't be reached, a preview keeps the file's artist tags and says so, and an album managed automatically waits and is looked at again by itself. When MusicBrainz now credits a release differently from the edition it was identified as, the artist tags are left as they are until it is identified again. The folder names follow the album artist, so a translated album artist moves the album folder, as a preview shows and Undo puts back. Profiles that already set these options start using them at the album's next run, and albums managed before have their credits fetched again once.

### Genres

With the profile's Genres section on, the genre tag is filled from the sources you list, in order: MusicBrainz (the release's, release group's and recordings' genres above the vote floor), ListenBrainz, Last.fm, and the genres the file already has. Names are spelled the way MusicBrainz's genre list spells them, aliases ("hip-hop", "dnb") become the canonical genre, and the allow, deny and casing lists apply. "Fill missing" only writes files without a genre, "merge" adds to what the file has. When ListenBrainz or Last.fm can't be reached and only MusicBrainz answered, the file keeps its genres and the preview says why.

### ReplayGain

With the profile's ReplayGain on, the preview measures each album's loudness (EBU R128 against -18 LUFS, the ReplayGain 2.0 reference) and writes track gain and peak, plus album gain and peak when "album aware" is on. "Preserve" never writes, "fill missing" only measures albums where a file lacks the values, "replace" always measures. Files are decoded one at a time, so a large album takes a while but never loads the machine more than one file at a time; an album that takes longer than ten minutes is left as it is and says so, and a run stops measuring after half an hour in all (later albums are measured next time). A file that stops decoding part way is not measured. Album gain and peak are only written when the whole album is in the run: picking single files writes their track values and leaves the album values as they are. A file measured once is not decoded again while it stays the same. With "required" on, a file that could not be measured waits.

## Artwork

With the profile's artwork on, the preview takes the album's front cover from the same Cover Art Archive cache the pages use (the release's, else its release group's). "Embedded" puts it into each file as the front cover, sized and encoded as the profile says, and keeps the file's other pictures; a file that already has this cover is left alone, and with "never replace with smaller" a larger cover stays, so a second run changes nothing. M4A files store no picture types: their first picture counts as the front cover. "External" writes `cover.jpg` (or `.png`, `.webp`) into the album folder, unless a `cover.*` file or a cover file matching the profile's patterns is already there; an existing file is never overwritten. The preview shows the art it will write. Undo puts the old embedded pictures back (FLAC and Ogg with their picture details as they were) and deletes the cover file it wrote, unless someone changed it since. "Restore originals" also deletes the cover and `.lrc` files Library Management wrote for the files it restores, while they still hold what it wrote.

## Lyrics

With the profile's Lyrics on, the preview asks LRCLIB for each file by its exact title, artist, album and length (within two seconds). Plain lyrics go into the file's lyrics tag; synced lyrics go into a `.lrc` file next to the track, named like it. "Preserve existing" keeps lyrics a file already has, and an existing `.lrc` file is never overwritten. LRCLIB is asked at most once a second, its answers are kept for a week ("no lyrics" for six hours), and when it asks for a pause every lookup waits that long. When LRCLIB can't be reached the preview says so; with "required" on, a file without lyrics waits. Undo takes the lyrics tag back off and deletes the `.lrc` file it wrote, unless someone changed that file since.

## Scrubbing

With "Scrub unmanaged tags" on, a run removes every tag outside the fields Library Management knows (an encoder note, a mood, a custom `TXXX` frame, ID3 URL, private and object frames), except the ones listed under preserved fields (a name like `mood`, or a tag named outright, such as `vorbis:MOOD`). Tags that belong to a field in the profile's field table are never scrubbed, whether the profile writes them or not (engineer, mixer, DJ-mixer, writer and director among them), and neither are publisher, ID3 grouping (`TIT1`, `GRP1`) or any MusicBrainz or AcoustID id. Only tags it can write back exactly are removed: an ID3 frame over 1 MB and an MP4 tag holding non-text or empty values stay as they are, and the preview says how many each file keeps and why. An MP3 whose ID3 tag holds a frame twice where the tag writer keeps only one (two identical pictures, say), or a FLAC or Ogg file that spells a tag two ways (`Mood` and `MOOD`) or holds an empty one, is left out of the run with the reason, since any write to its tags or art is refused. The preview lists each tag it removes with its values (a binary frame by its size). The removed values are kept with the run's undo and with the file's original, so undo and "Restore originals" put them back byte for byte. Embedded pictures stay unless "Preserve embedded art" is off; then the scrub removes them too (all but the front cover, when embedded art is on), and undo puts them back.

## The tag editor

The tag editor shows the file's tags next to any value you kept for it. Change a tag and pick how to keep it: "save" writes it and keeps it, so later Library Management runs leave it alone; "write once" only writes it; "reset" drops the kept value and puts the edition's value back. Album tags (album title, album artist, date, label and so on) change every file of the album. An edit is a preview like any other run: check it, apply it, undo it. Undoing a saved edit also puts the kept value back the way it was.

## Undo and restore

The first time Library Management changes a file it keeps the file's original tags and path. "Restore originals" makes a preview that puts the chosen albums back exactly as they were; apply it like any run. A file someone changed since, or whose old place is taken, is left alone with the reason. The kept tags, pictures and sidecar files Undo and "Restore originals" need are stored in the `undo` folder beside `library.db`, and backups carry them; if a saved copy is missing (a backup restored without it), only the file that needed it is left out and the rest of the run or album goes ahead. Once you no longer need them, the Automation tab of Library Management can delete the kept originals for good: it shows how many there are and asks you to type CONFIRM. It refuses while a restore or a file write is still running.

Files a plugin added to the library are listed under "Library files" on that plugin's card in Settings > Plugins. An admin can undo one there: the file is deleted only while it still holds what the plugin wrote, and the folder is scanned again so its track goes missing. See [PLUGINS.md](../PLUGINS.md).

## Editions and the edition sheet

Every album page of your library shows the album's edition on a plate under the artist and year: its name, who picked it ("Your choice", "Picked by DroppedNeedle" or "Best guess"), its year, country and formats, and how many of its tracks your files hold, with any that are missing or that you have in another version.

The album's track list follows the same edition. A track one of your files sits on shows that file's length. A track no file holds is marked "Missing" with the edition's length, and when you have it in another version, "Your version" and that file's length show under its title. Files the edition has no track for are listed once, under "Unmatched files", each saying why: "Another version of track 2", "Second copy of track 3" or "Not on this edition". The "In Library" badge counts the edition's tracks your files hold, out of all of them. The year beside the artist is when the album was first released; the plate shows the edition's own year.

Curators (admins and trusted users) press the plate, or open the album with `?edition=choose`, to open the edition sheet. It lists the edition you have now, the releases closest to your files, every other edition of the album, and search results: paste any MusicBrainz release link, even one from another album, or search MusicBrainz by title and artist. Pick one to see what taking it would do: a sentence on how many of your files fit it, and its tracklist beside your files, each track marked as fitting, missing, or another version of a track you have (one row with both lengths), followed by the files it has no track for and the second copies. Your files don't have to fit it one to one, and choosing never deletes anything: second copies, other versions and files the edition has no track for stay in the album with their own tags. An edition that fits none of your files can't be chosen.

"Use this edition" places your files on it, and the sheet stays open on what happens next: your files being matched to it, then its tags and file names being written in a folder DroppedNeedle manages by itself, or, in any other folder, a note that your files still carry their old tags until they are written. There, "Preview the new tags" lists each file's tags that would change (album, title, track, date, MusicBrainz IDs and so on), any cover or lyrics file it adds and any tag it removes, and counts the files that already carry them; nothing is written until you press "Write tags" under the list. What is written follows the folder's Library Management profile, as any run does: its fields, tagging scripts, the folder's own overrides, values saved for a file, artwork and lyrics. It never renames or moves a file, even when the profile does; a full run does that. It reaches only the files that sit on a track of the edition, so it leaves album ReplayGain as it is. The preview is a Library Management job, so it may wait behind other runs before it lists anything. Whoever wrote the tags can undo the write right there; admins can also undo it later from History. The preview waits until your files are matched to the edition, and is refused for an album that is left unmanaged or kept as your own track list. Undo is there throughout, and the sheet closes only when you close it.

"Keep this edition" confirms a best guess, and "Let DroppedNeedle choose" hands the album back to automatic best fit ("Let DroppedNeedle look again" on an album with no edition). On a custom edition it ends the custom edition. Its undo stays after DroppedNeedle has picked again, and puts your edition back, custom edition included. Taking an album's MusicBrainz match off from Needs a decision is undone the same way: undo puts back the match, its files' matches, the custom edition and any matching to the files that was waiting. With several copies of an album, the plate shows the copy the page shows and the sheet asks which copy you mean. On a phone the sheet fills the screen: pick an edition from the list, and "All editions" takes you back. Your pick sticks: later scans, retags, moves and downloads never replace it.

### Making your copy the edition

When an edition you pick has tracks your files don't hold, the sheet shows "Make your copy this edition" with two switches, "Get the missing tracks" and "Replace tracks you have in another version", both on by default. "Use this edition" then starts the download by itself, and the sheet lists each track it asks for under Next steps: waiting, fetching, added, failed, or held for you to check on the Downloads page. If it can't start (not enough disk space, for example), the reason shows there with "Try again", and the edition you chose stays chosen. While the download runs, Stop cancels it. When it fails or is stopped with tracks still missing, Retry starts a new download for just those tracks. The list shows while the download runs and after it fails or stops, also after you close the sheet and open it again, and the album page marks those tracks Fetching, Failed or Held instead of Missing while it runs or after it failed. With no download source set up, the download waits and starts by itself once one is saved; the sheet says so, with a link to the download settings. For the edition you already have, the same box offers the two as buttons. Replacing your versions comes in the same download as the missing tracks, so it needs "Get the missing tracks" on when there are any.

"Get the missing tracks" is one download for the album: it searches for the whole album, takes only the missing files from the most complete album folder it finds, and checks them against your edition. Tracks you already have that sit below your quality cutoff ride along in the same download, and each is replaced only if the new file is better.

With "Replace tracks you have in another version", a track you have in another version (the same title and artist, but not this edition's recording or length) is fetched in this edition's version too. When the new file is as good as yours or better, yours goes to the recycle bin and the new one takes its place, with its plays, favorites and playlist entries. When it is worse, yours stays and the new file is held; import the held file from the Downloads page or the album page and it replaces yours after all, with yours going to the recycle bin. Without it, or on an album DroppedNeedle leaves alone, your versions stay and are not fetched. The tracks it fetches join this copy of the album, in the folder with its other files, and are placed on its edition, even when your files carry another edition's tags. If you change the edition before they arrive, they still join this copy, as files the new edition has no track for. It needs enough free disk space where downloads land, and it says so plainly when there is not. With no download source set up it is held, and it starts by itself once a source is saved. It waits while another download of the album is still running.

### Files not on the edition

For the edition you have, "Move ... not on this edition to the recycle bin" lists the second copies and the files the edition has no track for; after you confirm, they move to the recycle bin, and "Put back", in the sheet or under "In the recycle bin" on the album's page, returns them. "Put back" does not replace a file that has since taken one of their places: then nothing is put back and the files stay in the recycle bin until you move that file out of the way. When the recycle bin is on the same disk as the album, each file moves back without being copied, so even a large album takes moments; across disks it is copied and checked. Each file comes back with its permission bits and modified time, and its track is listed again straight away, with its plays and favorites. A file whose copy is no longer in the recycle bin as it was (gone, or changed there) stays out, and the page names it; the rest come back. A file you already moved back by hand is listed again with them. If none are left, nothing changes. A file that was still waiting to move into the recycle bin comes back from where it waited. A file in a recycle bin that is no longer the one set in the settings comes back, and its copy is left there. Put back never follows a link someone made inside the library folder after the removal. If it stops part way (a crash, a full disk), it is finished or undone on restart, and the copies stay in the recycle bin until the files are home. Files left in the recycle bin are deleted once they are older than the recycle retention (30 days by default), or when an admin empties the recycle bin.

### Matching a file by hand

On the edition you have, a curator can put a file the edition did not place on a track no file holds: "Match to a track" on the file's row, or "It's this track" on a row showing another version. The file then counts as that track: later scans keep it, its tags and name follow the edition like any other file's, and when it takes the place of a file that went missing, that file's plays, ratings, favorites and playlist entries move to it. A track another file holds can't be taken. Matching a file on an edition DroppedNeedle picked makes the edition your choice, as "Keep this edition" does. If DroppedNeedle wrote the file that went missing, it can't tell the new file from your own retag of it, so it leaves the album as you have it until you choose "Manage it again". "Undo match" on the row puts the file back as it was; plays, ratings and favorites that moved stay. Once DroppedNeedle has written the track's tags to the file, the button gives way to a note: undo that write first (an automatic write is undone by an admin from History), then the match.

### Custom editions and leave unmanaged

When none of the editions is right, admins find two ways out under "None of these is right", at the end of the sheet's list. Each says what it does before you press it and takes effect at once; if one can't go through, the reason shows in its place. "Keep your own track list" (with a release selected) makes a custom edition. A custom edition keeps your files as they are, under the release group of a release you pick: their names, numbers and order are recorded, and no release is chosen. It is refused, with the reason, when the release's title or artist contradicts your files, when it belongs to another release group than the album's match, or when the files lack an album title, an album artist or a disc and track number of their own. "Leave this album unmanaged" drops the album's exact edition (its release group stays) and keeps Library Management away from its files until you press "Manage it again", which the album page then shows under its header. Both can be undone like any edition change: undo puts back the edition, the custom edition and "leave unmanaged" as they were. Choosing an edition or a custom edition for an album you left unmanaged keeps it unmanaged; "Manage it again" is the one way back.

An album you sealed as a custom edition (its files as they are, under a release group) is managed from what was sealed: the album and track names, numbers, year and genre recorded then. No release or release-track ID is written, and the file keeps any it has. If files were added to or removed from the album since, it waits until you seal it again. Automatic management leaves custom editions alone unless "Custom editions" is on for the library folder.

### Undoing an automatic edition

An edition picked automatically can be undone by an admin. The album and its tracks go back to exactly what they were before. Tracks you matched by hand are left alone. Once anything else changes the album, the undo is no longer offered.

### Undoing a split-album fold

When v2 split an album in two and every file of one half is tagged with the other half's release, the catalog cleanup folds that half into the other album and drops the match v2 gave it (see [Library](library.md)). The album page lists the fold under "Album history", and a curator can undo it there with Undo. The folded album comes back with its files, its v2 match, its "leave unmanaged" and its takeover mark, and the cleanup never folds it again. Plays, favorites, ratings, playlist entries and field overrides that moved to the album that kept the files stay there. Undo is not offered for a fold made before this version, or once a moved file was matched by a person, left the album or went missing.

### Edition preferences

Edition preferences (Settings > Editions) decide between editions that fit your files equally well, and which edition is fetched for an album you don't have yet: release types to avoid (live and compilations by default), status (official first), format (digital, then CD, then vinyl), country (your store region, then worldwide), earliest or latest date, and standard or deluxe. Your own pick always wins, then the fit to your files, then these.

## Automatic management

On the Automation tab of Library Management, turn a library folder on and pick when it should run (after downloads, after dropped folders are imported, or after a scan finds an album). Before it is saved, a dry run previews the whole folder under the new settings without changing anything; confirm it to switch on, and the operations page lists the dry run as confirmed. From then on, an album that lands or gets identified in that folder is organized with the folder's profile half a minute after it was last queued, once its identification has finished and no scan is running; work on other albums doesn't hold it back, but a running scan of any folder does. It uses the album's chosen edition. Albums whose match is still a best guess are skipped unless "Also manage unconfirmed matches" is on, albums you restored to their originals stay as they are, and a run where a file can't be managed waits on the operations page with the reasons instead of being applied. Changing the folder's profile or rules needs a new dry run. Albums it skips (an unconfirmed match, an out-of-date dry run, a restored album) are listed on the Library Management page with the reason and what to do; choosing a new edition for an album has it re-tagged and re-filed. An album in a folder or path rule set to Local metadata keeps its own tags: Library Management never retags or renames it, automatically or from a preview or an edition's tag write, and the preview and the skipped list say why. The tag editor still writes the fields you change there. Downloads that land in such a folder keep their own tags too: "Get missing tracks", an upgrade or a drop import places each file as it came and records its match without writing the release's tags, and the album page says "Folder keeps its own tags". An upgrade's old file, with your tags, goes to the recycle bin. Other downloads go to the first library folder that is Automatic where they would land, and only land in such a folder untagged when none is. Moving an album into such a folder is still allowed. If the profile asks for it, Jellyfin is told to rescan after each run (Plex and Navidrome have no rescan call yet and say so).

### Recheck and prepare identities

Recheck identities (admins, Library Management) asks MusicBrainz about albums that were matched automatically or carried over from v2, and writes a report: per album, whether the match still holds, with a short reason and what to do. Nothing changes until you apply it. Applying only removes matches where none of the files fit the release any more; those albums are then matched again, and each one can be undone from its album page. Editions someone picked by hand are listed but never removed.

Prepare identities (admins, Library Management) checks that every album file management may touch has an exact edition with each file placed on its track. Applying the report places the files where the edition supports it and uses the suggested edition for albums that have none (undo from the album page, as with any edition change). Each album in the report's "Choose edition" and "Needs review" lists has a "Choose edition" link to its edition sheet. You can also dismiss the report. With "Automatic edition acceptance" on in a Library Management profile, an album with no exact edition gets the suggested one on its own when it clearly fits: it scores at least 0.95, the matcher would accept it, and no other edition comes within 0.05 or ties it. Every edition that fits must also fit closely, not only the best one. An album someone picked an edition for is never changed this way. Because the bar is higher than for an ordinary automatic match, the edition is applied as confirmed, and it can be undone from the report or the album page, which also brings back the album's earlier state. Albums in folders set to keep their own tags are never looked up for either check. Both checks run in the background, can be paused, resumed or stopped, wait for scans, and retry albums later when MusicBrainz doesn't answer.

## Hand edits, takeover and "left unmanaged"

When you retag files that DroppedNeedle has tagged, it takes that as you taking over. The album keeps its edition, plays, favorites and playlist entries, DroppedNeedle stops retagging and renaming it, and the album page and Library Management show it as left unmanaged. So is an album you chose an edition for and then renamed by retagging its files, even if DroppedNeedle never wrote them. It keeps the edition, and "Manage it again" writes it.

New files that appear in the folder of an album you left unmanaged, kept as a custom edition or took over, or in a folder next to it, in the same scan that sees that album's files go, are left alone the same way when their lengths fit the files that went: DroppedNeedle cannot tell whether you retagged and renamed them. Library Management offers to merge the two albums. When a scan finds most of a library folder's files gone at once, it marks none of them missing, in case a drive is not mounted. The same goes for a drive or network share mounted inside a library folder: when a scan finds it empty, none of its files are marked missing and its albums are never merged into a copy you added in the meantime. If you removed that drive or share for good, remove its albums from the library. Until a scan finds the folder as expected again, DroppedNeedle does not retag or rename files that appeared in it since, in case they are your own retag, and Library Management lists those albums with the reason. If such a new album holds the same edition's tracks as an album whose files went since, the new album is left unmanaged at once as your retag when DroppedNeedle wrote the old album, when you chose the old album's edition (and not the new album's), or when the old album was left unmanaged, by you or after a change outside. A new album whose match is not settled when the folder is let go (a best guess, no match yet, or waiting for review) gets the same check once its match is settled, before DroppedNeedle writes anything to it. "Manage it again" hands it back. If you deleted some of the files on purpose, scans keep holding the folder until you remove the old albums from the library.

"Manage it again" on the album page hands it back: the files are then retagged and renamed from the album's edition, which overwrites your changes. A rename or tag edit you make in the app to a file you changed outside does not hand the album back. A tag edit in the app writes every tag DroppedNeedle manages from the edition, not only the one you edit, so its preview shows the values you changed by hand going back. Picard or beets renaming files as they retag counts as a retag.

A preview or a restore of the originals that covers more than one album leaves out an album with a file you changed outside that DroppedNeedle has not noticed yet, with the reason; in a folder managed automatically, that album is also left unmanaged. Preview or restore that album by itself to overwrite your changes. Changes DroppedNeedle does not manage do not count: a tag outside the profile's fields (unless the profile scrubs unmanaged tags, which would remove it), or a file you only moved, which it puts back where the naming rules say. Undoing one of DroppedNeedle's own runs in a folder it manages automatically also leaves the album unmanaged, so the run is not done again by itself. A tagger that runs on a schedule counts like a person: it takes an album over again the next time it runs after you hand the album back.

A FLAC file you replace at the same path with a new copy of the same recording, such as a re-rip or a higher-resolution copy, does not count as a hand edit. It counts as a new copy when its disc and track number are the same, its MusicBrainz recording ID matches the old file's (or, when either file has none, its title tag matches the old file's title tag and the lengths are within 5 seconds), and its sample rate, bit depth or channel count differs or its length moved by more than a second. DroppedNeedle then treats it as a file it has never written: in a folder it manages automatically it writes the album's edition into it, unless another file DroppedNeedle wrote on that album has gone missing, or the album is already unmanaged. The album page lists the new copy under "Album history". Undoing that run puts your copy back as it came and leaves the album unmanaged. Other formats, a copy with the same sound properties, and a copy the scan files under another album still count as a hand edit.

Restoring your music or the DroppedNeedle database from a backup makes every album DroppedNeedle wrote in between look changed from outside. It leaves those albums unmanaged and overwrites nothing. "Manage all again" on Library Management hands them back in one go.

## Retag joins

Moving, renaming or retagging music files yourself is fine. The next scan sees a moved file as the same track and a moved or retagged album as the same album, so favorites, play history, playlists and album matches stay put. An artist stays the same artist when its name changes in the tags, for example when Library Management translates or standardises names. When an album is matched to a MusicBrainz release, by DroppedNeedle or by you, each artist credited on it is linked to its MusicBrainz artist, as long as the album's credits line up with the release's one for one and each name matches the release's (as credited, or one of the artist's MusicBrainz names). Files that carry MusicBrainz artist IDs link their artists too. A linked artist keeps its favorites, plays, links and MusicBrainz page through a rename, and takes the new name once none of its files uses the old one. DroppedNeedle changes or removes a link it made when the album's match changes or the files name another artist, and never changes a link you made, except to follow an artist MusicBrainz merged into another. Two artist records MusicBrainz IDs in their files prove to be one artist are merged at the end of a scan, and the admin's duplicate artists list shows it. If MusicBrainz has merged an artist since your files were tagged, the old ID in your files and MusicBrainz's current ID count as the same artist. DroppedNeedle asks MusicBrainz about an artist ID only when it disagrees with a matched release or with other files. It keeps the old ID on file and never changes your files for it. Library Management writes the current ID the next time it writes the album, if your profile writes MusicBrainz IDs.

Other music put at a file's path, for example another album copied over an old one with the same file names, or a disc ripped over an old rip, comes in as a new track when its length differs by more than 5 seconds and its MusicBrainz recording ID differs too. When either file has no recording ID, the title tags must differ instead; a title taken from a file name never counts. The old track keeps its plays, favorites and playlist entries and shows as missing, and the album page lists it under "Album history". Putting the old file back brings the old track back.

A file you retag and rename in one go comes back as a new track. Once it is matched to the same track of the same album's edition as the file it replaced, its plays, ratings, favorites, playlist entries and saved places in player apps move to it, and the old track's links and the ids player apps saved open it. The same happens when one of two copies of a track is deleted, or, on an album whose edition DroppedNeedle chose, when a download brings back a track whose file is gone. A file a scan adds to an album whose edition is set is placed on that edition's track when its own MusicBrainz ids say which one: its release track id, or its release and recording ids at the same disc and track number. Names alone never place a file. A copy a scan saw beside the original takes the original's place when the original is deleted. This move cannot be undone. The album page lists these moves, and the albums joined into it, under "Album history" for 180 days.

Two copies of an album in different folders (say a FLAC and an MP3 copy) stay two albums. A retag that more than one scan sees (half the files today and the rest tomorrow, or a scan stopped half way) is joined into one album, under the new name, once a scan has seen the rest; the old album's links still open it. Until then the half already retagged is left the way the old album was, so if you had left that album unmanaged, DroppedNeedle does not touch the new half either.

Retagging the files you keep and deleting the rest is joined a scan later, or a day later when you deleted half the album or more. An album you retag to a new name with its MusicBrainz ids removed and rename in one go first comes back as a new album. Once DroppedNeedle matches the new album to the same edition as the old one, the two are joined under the new name, the old album's links open it, and its tracks keep their plays, favorites and playlist entries. If the new album is matched to another edition, choose the old album's edition for it and they are joined then. If DroppedNeedle had written the old album's files, it then leaves the joined album alone until you choose Manage it again. A retag begun before this version is not joined this way.

Some retags are not joined by the scan, because a wrong guess would put an edition on the wrong files: when the old and the new album each have a different edition someone chose, when the old album has a custom edition, or when some of its tracks were moved to another album earlier (an album split in two looks the same as one renamed). Admins see these pairs on Library Management, under the albums left unmanaged, as "pairs of albums might be one album retagged", and on both albums' pages. Each card says why, and offers "Merge into one album" or "Keep them apart". When both albums have a chosen edition, you pick which one to keep first. Merging keeps the new album and moves the old album's favorite, plays and playlist entries to it; its links open the new album. A custom edition on the old album does not carry over and can't be put back, and the card says so before you merge. If the old album's chosen edition is kept and DroppedNeedle never wrote these files, the album is left unmanaged until you choose "Manage it again", which writes that edition's tags. "Keep them apart" marks them as two albums, and later scans leave them so. If either album changed since the card was shown, the merge is refused and the card asks you to look again.

## Safe placement and the recycle bin

When a preview can't place a file because another file already sits at its new path, open the file and settle it: keep both where they are, put the new file next to the old one under another name, or move one of the two to the recycle bin (the one in the way, so the new file takes its place, or the new one). Each choice is a small preview of its own, and the recycle bin keeps the file in a dated folder. A new file you send to the recycle bin this way can be put back from its album's page; an old file the new one replaced can only be moved back by hand, since the new file holds its place (the Recycle Bin page lists it). When the new file takes the old one's place, the old file is set aside first and only goes to the recycle bin once the new one is in; if the write stops part way (a crash, a full disk), the old file is put back or the write is finished on restart, never lost. The result names the folder in the recycle bin. Files are never overwritten.

### Adding files safely

DroppedNeedle adds a file to a library folder only when its name is free, so it cannot replace a file another program put there in the meantime. A few disks give it no way to do that (no hard links, and no rename that refuses a taken name). It checks a library folder the first time it writes there, and for such a disk the folder's card on the Automation tab of Library Management shows a warning, "Files can be overwritten in this library": The disk under "<library name>" has no way to add a file only when its name is free. DroppedNeedle checks that the name is free and then moves the file in. If another program creates a file with that name in the moment between, that file is replaced. Keep other programs from writing to this library while DroppedNeedle manages it, or move it to a disk that supports hard links, such as ext4 or an NFS share. Library Management keeps working in such a folder. A folder nothing has been written to yet says "Not checked yet". "Check again" runs the check now: it creates a folder named `.droppedneedle-management-probe` at the top of the library folder and removes it again. If the check cannot finish (a full or read-only disk, a share that does not answer), it says so and the last result stays. The result is kept until the server restarts or the list of library folders changes.

### Interrupted writes and leftover files

If the server stops during a run, at the next start each album whose files were all staged is finished and any other album is put back as it was. A write that fails or is put back removes the folders it made for its files, once they are empty; a folder that was there before is never removed. If DroppedNeedle ever stops in the middle of writing files and can't tell for sure how to finish or undo it, it leaves everything in place and lists the write under "Some file writes need you" on the Library Management page, with the files involved. Check the files are where they should be, then mark the write as handled; that changes nothing on disk. A write it has been retrying for more than a day (a library folder that is missing, read-only or full) is listed there too, as still being retried; it keeps trying. And each time the server starts it looks through the library folders for hidden working files (their names start with `.droppedneedle-management-`) that are more than a day old and that no write accounts for, which a power cut can leave behind. It lists them as leftover temporary files and never deletes or moves one itself. After that start and an id, each name carries the file's own name, cut short if it is long. A name ending in `.bak` is a file as it was before the write and is complete; one ending in `.tmp`, or with `.staging` before the file type, is a copy that was still being made and may be cut short. If the file with the normal name beside it plays, delete the hidden one; if it is missing, copy the hidden one to the normal name and check it plays before deleting anything.
